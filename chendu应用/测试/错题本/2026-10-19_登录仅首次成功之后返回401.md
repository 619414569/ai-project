# BUG-20261019-001

| 项 | 值 |
| --- | --- |
| 编号 | BUG-20261019-001 |
| 日期 | 2026-10-19 |
| 严重度 | 高（阻塞，登录主流程不可用） |
| 状态 | resolved |
| 模块 | `backend` 安全认证（`SecurityConfig`） |
| 环境 | 本地开发（JDK 17、Spring Boot 3.3.5、PostgreSQL 14） |

## 摘要

后端进程启动后，登录接口 `/api/v1/auth/login` 只有第一次调用成功，从第二次起全部返回 `401`，且凭据本身正确。

## 原始错误

HTTP 响应：

```json
{
  "code": "UNAUTHORIZED",
  "message": "Username or password is incorrect",
  "traceId": "769d67d601f845f09a3b831f879b041d",
  "timestamp": "..."
}
```

服务端日志：

```text
WARN [...] o.s.s.c.bcrypt.BCryptPasswordEncoder : Empty encoded password
```

## 根因

`com.aiproject.scaffold.security.SecurityConfig#userDetailsService` 在 Bean 初始化阶段构建了一个**单例** `UserDetails` 并在每次 `loadUserByUsername` 时复用同一实例：

```java
UserDetails userDetails = User.withUsername(demoUser.username())
        .password(passwordEncoder.encode(demoUser.password()))
        .roles(demoUser.roles().toArray(String[]::new))
        .build();
return username -> { ...; return userDetails; };
```

认证成功后，`ProviderManager`（默认 `eraseCredentialsAfterAuthentication = true`）调用 `AbstractAuthenticationToken.eraseCredentials()`，该方法会同时擦除 **credentials 与 principal** 的凭据。`org.springframework.security.core.userdetails.User` 实现了 `CredentialsContainer`，因此该单例对象的 `password` 字段被置为 `null`。

此后每次登录都会执行 `passwordEncoder.matches(rawPassword, null)`，BCrypt 产生 `Empty encoded password` 告警并返回 `false`，最终抛出 `BadCredentialsException`，表现为 `401`。

**特征**：重启进程后第一次登录必然成功，之后全部失败。这个特征容易误导为数据库或 Redis 可用性问题。

## 修复

改为每次认证查询时构建新的 `UserDetails` 实例，BCrypt 散列值只计算一次：

```java
@Bean
UserDetailsService userDetailsService(SecurityProperties properties, PasswordEncoder passwordEncoder) {
    SecurityProperties.DemoUser demoUser = properties.demoUser();
    String configuredUsername = demoUser.username();
    String encodedPassword = passwordEncoder.encode(demoUser.password());
    List<String> roles = demoUser.roles();
    return username -> {
        if (!configuredUsername.equals(username)) {
            throw new UsernameNotFoundException(username);
        }
        return User.withUsername(configuredUsername)
                .password(encodedPassword)
                .roles(roles.toArray(String[]::new))
                .build();
    };
}
```

同时移除不再使用的 `UserDetails` 导入，新增 `UsernameNotFoundException` 导入。

## 可重复回归用例

自动化测试已固化：`backend/src/test/java/com/aiproject/scaffold/auth/AuthIntegrationTest.java#repeatedLoginAlwaysSucceeds`，连续 5 次登录均断言 `HTTP 200`、`code=OK`、`accessToken` 非空。执行方式见 [测试记录](../测试记录/2026-10-19_登录与跨域回归测试记录.md)。

前置：后端已启动，PostgreSQL 与 Redis 地址按 `application.yml` 配置可达。

```powershell
$body = '{"username":"admin","password":"Admin@123456"}'
1..5 | ForEach-Object {
  try {
    $r = Invoke-WebRequest -Uri "http://localhost:8080/api/v1/auth/login" `
           -Method Post -Body $body -ContentType "application/json" -UseBasicParsing
    "第 $_ 次 -> HTTP $($r.StatusCode)"
  } catch { "第 $_ 次 -> HTTP 401" }
}
```

**期望结果**：5 次全部返回 `HTTP 200`，响应体 `code` 为 `OK`。

**修复前的实际结果**：第 1 次 `200`，第 2 至 5 次均为 `401`。

## 防复发措施

- `UserDetailsService` 一律在每次 `loadUserByUsername` 调用时返回新实例，禁止跨请求复用 `UserDetails` 对象。
- 排查登录失效时，先确认「重启后是否仅首次成功」这一特征，再据此区分凭据擦除与中间件可用性问题。

## 修复后验证

| 项 | 结果 |
| --- | --- |
| 连续 4 次登录（直连 8080） | 全部 `HTTP 200` |
| 经 Vite 代理 `Origin: http://localhost:5173` | 登录 `code=OK` |
| 经 Vite 代理 `Origin: http://127.0.0.1:5173` | 登录 `code=OK`，`token` 长度 191 |
| `GET /api/v1/auth/me`（携带 Bearer Token） | `code=OK`，`user=admin`，`roles=ADMIN,USER` |
| `GET /actuator/health` | `503`（Redis 未启动，已知且不阻塞登录） |

## 后续演进（2026-10-19）

同日将登录校验由「配置项构造账号」改为「数据库 `workbench_user` 表校验」后，
`SecurityConfig` 中返回单例 `UserDetails` 的 `userDetailsService` Bean 已被**整体移除**，
`authenticationManager` 改为注入 `DatabaseUserDetailsService`。

因此本条记录描述的单例复用问题不再存在；`repeatedLoginAlwaysSucceeds` 用例保留，
作为连续登录可用的回归保障。详见 [2026-10-19 V1.1 版本日志](../../提交日志/2026-10-19_V1.1.md)。
