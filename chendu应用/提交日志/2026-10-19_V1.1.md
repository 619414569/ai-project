## 变更类型

小功能增加：登录校验方式由配置项构造账号改为数据库账号认证，并新增演示账号。

## 变更摘要

### 1. 新增 `workbench_user` 表（Flyway `V2`）

新增迁移文件 `backend/src/main/resources/db/migration/V2__create_workbench_user.sql`，
创建登录账号表，含 `username`（主键）、`password_hash`、`roles`、`password_change_required`、
`active`、`created_at`、`updated_at` 字段，并为表和每个字段写入中文业务用途备注（规则 7.3）。

### 2. 新增 `DatabaseUserDetailsService`

`backend/src/main/java/com/aiproject/scaffold/user/DatabaseUserDetailsService.java`

实现 `UserDetailsService`，通过 `JdbcTemplate` 按 `username` 查询 `workbench_user` 表，
每次认证返回新的 `UserDetails` 实例（规避 BUG-20261019-001 的单例凭据擦除问题），
并把 `active` 字段映射为 `disabled`、把逗号分隔的 `roles` 解析为 `ROLE_` 权限。

同时提供 `updatePassword`、`isPasswordChangeRequired`、`listActiveUsernames` 三个方法，
用于后续接入改密与账号管理。

### 3. 改造 `SecurityConfig`

`backend/src/main/java/com/aiproject/scaffold/security/SecurityConfig.java`

删除原先返回单例 `UserDetails` 的 `userDetailsService` Bean 及其不再使用的导入
（`User`、`UsernameNotFoundException`）。`authenticationManager(UserDetailsService, ...)`
改为注入 `DatabaseUserDetailsService`，认证链路由配置校验切换为数据库校验，接口签名不变。

### 4. 新增 `DemoUserInitializer`

`backend/src/main/java/com/aiproject/scaffold/config/DemoUserInitializer.java`

实现 `ApplicationRunner`，在应用启动时把配置项声明的演示账号以 BCrypt 散列写入
`workbench_user` 表。只插入缺失账号，已存在账号不覆盖，可重复执行。
由 `APP_DEMO_DATA_ENABLED`（`app.demo-data.enabled`）控制开关，便于生产环境关闭播种。

配套改动：

- `SecurityProperties` 新增 `additionalDemoUsers` 列表配置；
- `application.yml` 新增 `app.demo-data.enabled` 与 `additional-demo-users` 配置段；
- `.env.example` 同步新增 `DEMO_DCY_USERNAME` / `DEMO_DCY_PASSWORD` / `DEMO_DCY_ROLES` / `APP_DEMO_DATA_ENABLED`。

### 5. 播种演示账号 `admin` 与 `dcy`

| 用户名 | 角色 | 口令来源 |
| --- | --- | --- |
| `admin` | `ADMIN,USER` | `DEMO_ADMIN_PASSWORD`（沿用原有配置，未变更） |
| `dcy` | `USER` | `DEMO_DCY_PASSWORD` |

口令明文不写入文档（规则 8.7），实际取值见 `application.yml` 与 `.env.example`。

### 6. 测试补充

新增 `backend/src/test/java/com/aiproject/scaffold/user/DatabaseUserDetailsServiceTest.java`（9 例），
覆盖数据库账号加载、散列校验、账号停用、角色解析、改密落库、启用账号列表。

改造 `backend/src/test/java/com/aiproject/scaffold/auth/AuthIntegrationTest.java`：
启用 Flyway（认证已依赖 `workbench_user` 表）、按正常启动路径播种演示账号、
移除测试源码中硬编码的口令，并新增 3 例覆盖 `dcy` 登录、不存在账号、多账号交替连续登录。

### 7. 本机建库，并与 `619414569应用` 统一为 `ai_scaffold`

本机实例原先只有 `brilliant-idea`，没有 `ai_scaffold`。本次在本机创建角色与库 `ai_scaffold`，
并把连接切过去，与 `619414569应用` 的配置（库 `ai_scaffold`、角色 `ai_scaffold`）保持一致：

| 文件 | 改动 |
| --- | --- |
| `数据/初始化/00_create_database.sql` | 新增幂等脚本，创建角色 `ai_scaffold` 与库 `ai_scaffold`（属主 `ai_scaffold`）；只建角色与库，不含建表 DDL |
| `backend/src/main/resources/application.yml` | `DB_URL` 默认库名、`DB_USERNAME`、`DB_PASSWORD` 默认值改为 `ai_scaffold` / `ai_scaffold` / `change-me-postgres` |
| `docker-compose.yml` | `POSTGRES_DB` 与 backend `DB_URL` 的库名保持 `ai_scaffold`，与本机一致 |
| `.env.example` | `POSTGRES_DB`、`DB_URL` 保持 `ai_scaffold` |
| `README.md` | 本地地址与 PolarDB-PG 连接示例的库名保持 `ai_scaffold` |

表、迁移与演示账号不由脚本创建，而是应用首次启动时由 Flyway（`V1`、`V2`）与 Flowable
（`act_*`、`flw_*` 共 38 张）建立，`DemoUserInitializer` 播种 `admin` 与 `dcy`。

> 中途曾一度把库名改为 `brilliant-idea`，本轮按「与 `619414569应用` 一致」的要求回退为
> `ai_scaffold`，相关配置、脚本与文档已全部同步修正。

## 已知未覆盖项

| 项 | 原因 |
| --- | --- |
| RocketMQ 消息发布与消费 | 本机 Docker 不可用，无 RocketMQ 服务 |
| Redis 缓存读写 | Redis 未启动，`/actuator/health` 返回 `503` |
| Flowable 工作流 | 集成测试中停用自动建表；BPMN 文件当前为 `.disabled` |
| 改密接口端到端 | 本版本仅提供 `updatePassword` 落库能力，未新增 HTTP 改密接口 |
| 前端浏览器点击链路 | 未引入浏览器自动化 |
| 生产环境（PolarDB-PG）迁移执行 | 本轮仅在本地开发库执行 |
| Compose 编排启动与容器内建库 | 本机 Docker 不可用，无法执行 `docker compose up`，仅验证配置默认值 |
| 与 `619414569应用` 共用同一库 | 两应用的迁移 `V1`、`V2` 内容不同，共用同一库会因 Flyway 校验失败而无法启动。本轮只让 `chendu应用` 连接 `ai_scaffold`，未与 `619414569应用` 联调；若后续要共用，需调整迁移版本号 |

## 回滚方案

| 步骤 | 操作 |
| --- | --- |
| 1 | 停止后端进程 |
| 2 | 回滚代码：恢复 `SecurityConfig` 的单例 `UserDetailsService` Bean 并删除 `V2` 迁移、`DatabaseUserDetailsService`、`DemoUserInitializer` |
| 3 | 数据库回滚：执行 `DROP TABLE IF EXISTS public.workbench_user;` 并删除 `flyway_schema_history` 中 `version = 2` 的记录 |
| 4 | 重新构建并启动，验证登录恢复为配置校验 |

> 仅回滚代码而不清理数据库会导致 Flyway 校验失败（历史中存在 `v2` 记录但代码已无该迁移），两步必须同时执行。
