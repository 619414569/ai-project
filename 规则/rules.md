# AI 项目研发与交付规则

版本：V1.0
生效日期：2026-10-15
适用范围：本仓库内所有用户、智能体、个人应用、脚手架维护、测试、部署、生产操作和 Git 操作。

## 1. 规则效力与修改控制

1. 本文件是仓库研发、数据、测试、验收、发布和智能体行为的唯一权威规则源。
2. 智能体开始任何任务前，必须完整读取本文件，并在任务全过程中遵守。
3. 本文件属于受保护文件。智能体不得自行新增、删除、改写或弱化规则。
4. 修改本文件前，必须先向用户说明拟修改条款、修改原因和影响，得到用户对本次规则修改的明确确认后才能修改。
5. 用户确认某项业务、代码或生产操作，不等同于确认修改本规则；规则修改必须单独说明。
6. 新指令与本文件冲突或含义不明确时，停止冲突部分，向用户说明冲突点并等待明确决定。
7. 本文件的首次创建由用户在 2026-10-15 的当前指令明确授权。

## 2. 用户、目录与所有权

1. `{username}` 默认取当前仓库 `git config user.name`；不得根据操作系统用户名、目录名或登录账号擅自替代。
2. 每个用户的应用交付统一放在一级目录 `{username}应用/`。
3. 应用源码、配置、原型、测试、数据、文档和提交日志必须放在对应 `{username}应用/` 的二级目录内。
4. 不得修改、删除、覆盖或提交其他用户的内容，除非用户明确指定协作范围并确认。
5. `规则/rules.md` 是仓库级文件，不归属于任一用户应用。

## 3. 脚手架任务边界

1. 只有用户单独明确说明“本次是脚手架维护、升级、恢复或提交”时，才处理 `脚手架/**`。
2. 用户未单独说明脚手架任务时，一律按非脚手架任务处理：不操作 `脚手架/**`，也不执行脚手架关联判断、差异检查或重复汇报，直接跳过该目录。
3. 脚手架任务必须单独说明变更范围、测试范围和影响，并与任何个人应用变更分开提交。
4. 不得把个人应用的业务代码、配置、数据、原型或测试反向同步到 `脚手架/**`。
5. 应用确需新增底座能力时，应提出独立脚手架任务，不得在应用任务中顺带修改脚手架。

## 4. Git 分支与提交规则

1. 每个用户使用自己的长期工作分支，统一命名为 `user/{username}`。
2. 开始用户工作前，应确认当前提交人和当前分支；个人应用的开发、修复、文档、测试、数据脚本、版本日志和推送都聚焦于该用户分支。
3. 用户分支不存在时，从 `main` 创建；已存在时切换到该分支并确认与远端关系，不得重复创建含义相同的分支。
4. `main` 是主分支，不接受个人功能、修复、文档或数据变更的直接提交。
5. `main` 只用于合并已经验收通过的用户分支；不得在 `main` 上补写独立提交来绕过用户分支。
6. 用户分支只能提交本用户任务范围内的文件。发现其他用户或未知来源的改动时必须保留，不得擅自回退、覆盖或混入提交。
7. 禁止强制推送、重写公共历史或使用破坏性 Git 命令，除非用户明确授权并已说明恢复方案。
8. 未达到验收与提交门禁时，可以创建或切换分支，但不得提交、推送或合并。

## 5. 标准任务流程

1. 读取本规则和任务相关文档。
2. 确认当前 Git 提交人、个人分支、应用目录和工作区现有改动。
3. 明确本次任务范围、验收标准、潜在生产影响和不在范围内的内容。
4. 提报 Bug 或处理报错前先检索错题本，确认是否为历史同类问题。
5. 先完成设计或测试用例，再进行实现；小型文档任务可以直接定义可验证检查项。
6. 实现过程中只修改任务必要文件，不做无关重构或目录迁移。
7. 执行与风险匹配的单元测试、集成测试、构建、部署或生产只读验证。
8. 更新测试记录、数据说明、错题本、版本日志和验收状态。
9. 技术检查完成后将验收状态保持为 `pending`，向用户报告实际结果并等待人工验收。
10. 收到有效验收口令后再执行提交门禁，提交并推送到用户分支；`main` 后续只执行合并。

## 6. 生产数据库操作审批

### 6.1 必须事前确认的操作

任何会改变生产数据库状态的操作都必须在执行前获得操作人的明确确认，包括但不限于：

- `INSERT`、`UPDATE`、`DELETE`、`TRUNCATE`、数据导入和数据修复；
- `CREATE`、`ALTER`、`DROP` 表、字段、索引、约束、序列、视图或函数；
- 执行 Flyway、Liquibase、Flowable 自动建表或其他迁移；
- `COMMENT ON`、权限调整、所有者调整和其他元数据写入；
- 会间接写库的应用启动、初始化器、批任务、消息消费或管理接口调用。

只读 `SELECT`、系统目录查询和不产生数据库对象的只读导出可以直接执行，但必须限制范围、避免输出敏感值，并说明查询结果来自生产环境。

### 6.2 确认内容

执行前必须向操作人明确列出：

1. 目标环境、数据库和 schema。
2. 每一张拟修改表的完整名称。
3. 操作类型及拟修改的字段、内容或结构。
4. `WHERE` 条件、目标主键或明确的数据集合；不得只写“修改相关数据”。
5. 预计影响行数；不能预估时先执行只读统计。
6. 是否新增业务表。新增业务表必须单独说明表名、业务目的、主要字段、主外键、索引、数据生命周期和兼容影响，并单独获得确认。
7. 对现有业务、权限、接口、部署和历史数据的影响。
8. 事务、备份、回滚和执行后验证方案。

涉及密码、令牌或密钥时，确认内容只描述来源和处理方式，不展示明文或完整哈希。

### 6.3 确认与执行边界

1. 只有操作人明确同意所列目标表和修改内容后才能执行。
2. 确认只对当次列明范围有效；表、字段、条件、数据内容或影响范围发生变化时必须重新确认。
3. “本次验收通过”是交付验收口令，不替代生产数据库写操作确认。
4. 用户要求修改代码或编写 SQL，不代表已经批准在生产执行该 SQL。
5. 未获确认时，只能做本地实现、静态检查、只读盘点和回滚方案准备。

### 6.4 执行与结果校验

1. 写操作优先使用事务和遇错即停机制；高风险操作先备份或生成可验证回滚材料。
2. 可以回滚演练的脚本，应先演练再正式提交。
3. 禁止使用范围不明确的条件、未经校验的变量、交互式无限等待或把密码写进命令历史。
4. 执行后独立核对影响行数、关键数据、约束、关联关系和业务计数。
5. 向用户报告实际执行对象、成功或失败结果、影响数量、验证证据和回滚状态。
6. 任何失败、超时或部分执行都必须立即停止后续写入并记录错题本，不得用后续成功覆盖原错误。

## 7. 代码与数据库结构变更

1. 数据库结构变更必须使用新增的版本化迁移文件；已经在共享环境执行过的迁移文件不得修改。
2. 新增业务表前，除生产审批外，还必须说明领域归属、表职责、字段含义、主键、外键、唯一约束、索引、审计字段和清理策略。
3. 表和字段必须写实际业务用途备注，不得只复述名称或数据类型。
4. 后端接口保持统一响应结构、稳定错误码、参数校验、鉴权和请求追踪标识。
5. 前端和后端应可独立构建、发布和运行；环境差异通过配置注入，不硬编码本机地址、生产地址或凭据。
6. 默认拒绝未授权访问和越权修改；任何新增接口都要明确公开、登录可用或角色受限。

## 8. 输入校验规则

1. 所有外部输入必须在系统边界校验，包括 HTTP 参数、请求体、文件、URL、环境变量、消息、数据库导入和命令参数。
2. 必须校验必填性、类型、长度、范围、枚举、格式、编码、业务唯一性和关联对象存在性。
3. 身份标识、资源 ID 和用户名必须结合当前登录用户做权限校验，不得只依赖前端隐藏按钮。
4. SQL 使用参数化查询或结构化数据库 API，不拼接不可信输入。
5. 文件路径必须规范化并限制在允许目录内，拒绝绝对路径、父目录穿越、编码绕过和索引外文件。
6. URL 必须限制协议和目标类型，拒绝 `javascript:` 等危险协议；外部跳转和跨域来源按白名单处理。
7. 密码、令牌、密钥和生产连接信息不得写入源码、测试快照、日志、提交记录或普通文档。
8. 破坏性文件、容器、Git 和数据库操作必须解析并核对精确目标，禁止对宽泛目录或未知集合执行。

## 9. 输出校验规则

1. API 输出使用统一结构，至少包含稳定业务码、消息、数据和可追踪标识；HTTP 状态与业务结果保持一致。
2. 不向客户端、日志、测试报告或终端输出明文密码、完整令牌、私钥、数据库密钥或无必要的个人敏感信息。
3. 错误响应不得泄露堆栈、SQL、服务器路径和内部凭据；服务端日志保留可定位的请求 ID 和必要上下文。
4. 列表、分页、排序和筛选结果必须验证数量、顺序和过滤条件，不得仅以 HTTP 200 判定通过。
5. 文件下载或在线预览必须校验文件身份、内容类型、编码和访问权限；Markdown/HTML 渲染必须防止脚本注入。
6. 自动化脚本必须根据真实退出码和关键字段判定结果，禁止无条件输出“成功”。
7. 测试和生产验证结论必须区分“未执行”“通过”“不通过”“阻塞”，不得用推测代替证据。

## 10. 错题本规则

1. 所有缺陷、命令错误、构建失败、部署失败、生产操作异常和校验脚本错误都要记录在对应应用的 `测试/错题本/`。
2. 提报或修复前必须按错误消息、接口、模块和环境检索已有记录。
3. 同类问题复发时在原记录追加时间、环境、遗漏原因、影响、修复和防复发措施，不重复创建新编号。
4. 新问题必须记录编号、日期、严重度、状态、摘要、原始错误、根因、修复和可重复回归用例。
5. 没有回归用例或验证证据，不得把问题标记为 `resolved`。
6. 发布门禁要求所有问题均为 `resolved`，并人工复核错题本，不能只依赖脚本退出码。

## 11. 测试、验收与发布门禁

1. 功能开发完成后必须先更新测试文档，再按文档逐条执行并记录真实结果。
2. 风险涉及共享契约、权限、数据库、部署或用户主流程时，必须补充相应集成或端到端测试。
3. 自动化测试、构建、部署、健康检查和回归全部通过，只代表技术检查完成，不代表用户验收通过。
4. 唯一验收口令是用户单独输入完整文本：`本次验收通过`。
5. 未收到有效验收口令时，验收状态必须为 `pending`，不得提交、推送、合并或宣称最终验收通过。
6. 验收口令只覆盖当时明确列出的变更和测试结果。确认后如果代码、配置、数据、迁移、规则、文档或测试结论再次变化，状态立即恢复为 `pending`，必须重新测试并再次验收。
7. 收到验收口令后仍须执行发布门禁；门禁失败时不得提交，修复后验收状态重新变为 `pending`。
8. 生产部署的最终标准必须包含实际外部入口验证；本机、容器内或服务器本地访问成功不能代替外部访问。

## 12. 版本与更新日志

1. 初始版本为 `V1.0`。
2. 向后兼容的修复和小功能增加递增小数位，例如 `V1.0` 到 `V1.1`。
3. 架构重构、不兼容变更或产品范围显著扩展递增整数位并重置小数位，例如 `V1.9` 到 `V2.0`。
4. 每次版本更新新增独立 Markdown 日志，不覆盖历史版本。
5. 文件名格式为 `YYYY-MM-DD_V<major>.<minor>.md`，按文件名倒序展示。
6. 日志按 Git 提交人归档，必须记录时间、版本、变更类型、变更摘要、测试结果和影响范围。
7. 版本号、应用构建版本、镜像标签、更新日志索引和网页展示必须保持一致。

## 13. Git 提交前检查

提交和推送前必须全部满足：

1. 当前分支为 `user/{username}`，不是 `main`。
2. 变更范围与用户确认的任务一致，不包含其他用户文件或未知修改。
3. 没有 `.env`、私钥、令牌、明文密码、完整密码哈希、Office `~$` 锁文件、构建缓存或临时产物。
4. 工作区和暂存区空白检查、语法检查、测试、构建及必要的部署验证通过。
5. 错题本无 `open` 项，相关回归用例通过。
6. 测试记录、数据说明、版本日志和索引已同步。
7. 验收状态为 `accepted`，且对应当前未变化的变更范围。
8. 提交信息准确描述范围；提交完成后核对提交内容，再推送当前用户分支。
9. 推送后核对远端分支提交 SHA；不得默认把用户分支直接更新到 `main`。

## 14. 部署与运行门禁

1. 部署前明确目标服务器、目录、端口、域名、镜像版本、数据依赖和回滚版本。
2. 配置通过环境变量或密钥服务注入，生产密钥不得进入仓库或命令输出。
3. 数据库迁移与生产数据修改分别执行对应审批，不得隐藏在容器启动或应用初始化中。
4. 部署后检查容器状态、健康接口、应用日志、依赖连接和外部页面。
5. 涉及登录、权限或跨域时，必须从真实外部 Origin 验证，不得只用无 Origin 请求代替浏览器链路。
6. 失败时保留现场和日志，停止扩大变更，按已验证方案回滚并更新错题本。

## 15. 智能体输入与交付输出

1. 智能体必须以用户最新指令为准，不能把历史授权扩展到新的生产写入、规则修改、脚手架任务、提交或合并。
2. 需求有合理默认值且不扩大权限时可以自主推进；会改变业务口径、生产数据、规则、分支历史或外部系统状态时必须先确认。
3. 执行前说明本次将修改的范围；生产写操作必须使用第 6 节的确认清单。
4. 执行中报告关键进展和错误，不隐藏失败，不把计划描述成已完成结果。
5. 交付时必须说明：实际变更、验证结果、未完成项、验收状态、Git 分支以及是否已提交/推送/合并。
6. 未执行的检查必须明确说明原因；不得声称“没有问题”或“可以发布”。
7. 任何输出中的文件、表、接口、端口、版本和数量应使用实际检查结果，不凭空推断。

## 16. 最小执行检查表

智能体每次任务至少核对以下事项：

- [ ] 已完整读取 `规则/rules.md`。
- [ ] 已确认 Git 提交人和 `user/{username}` 分支。
- [ ] 已明确任务范围和验收标准。
- [ ] 非脚手架任务已直接跳过 `脚手架/**`。
- [ ] 生产写操作已逐表逐内容说明并获得单独确认，或本次没有生产写操作。
- [ ] 新增业务表已单独说明并获得确认，或本次没有新增业务表。
- [ ] 已检索并维护错题本。
- [ ] 已完成输入、输出、权限和敏感信息校验。
- [ ] 已按测试文档执行并记录结果。
- [ ] 变更后验收状态为 `pending`，或已收到覆盖当前范围的有效验收口令。
- [ ] 提交前门禁全部通过。
- [ ] 只向用户分支提交和推送；`main` 仅用于合并。
